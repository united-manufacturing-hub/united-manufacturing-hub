# Releasing umh-core

## Overview

All development happens on `staging`, and releases are cut from it. The `main` branch is no longer used.

A bot keeps one release PR open against `staging`, titled "Release umh-core vX.Y.Z". Approving and merging it is the stable release. A pre-release (nightly) is still published by hand.

## Changelog convention

`CHANGELOG.md` is generated by [changie](https://changie.dev). Never edit it by hand. During development, each PR adds a fragment to `.changelog/unreleased/` with `make changelog`. The release PR moves all fragments into `.changelog/X.Y.Z.md` with `make release-changelog VERSION=X.Y.Z` and regenerates `CHANGELOG.md` with a `## [X.Y.Z]` section.

## Pre-release (nightly)

1. Go to [Releases > Draft a new release](https://github.com/united-manufacturing-hub/united-manufacturing-hub/releases/new)
2. Create a **new tag** with the format `v0.X.Y-pre.N` (e.g., `v0.44.10-pre.1`)
3. Target: `staging`
4. Check **"Set as a pre-release"**
5. Body can be minimal — pre-releases don't get changelog sync or release notes automation
6. Click **Publish release**

### What happens automatically

| Workflow | Trigger | What it does |
|----------|---------|-------------|
| `build-umh-core.yml` | `v*-pre.*` tag push | Builds Docker image, pushes it to GHCR as `v0.X.Y-pre.N` (not `latest`), verifies binaries, notifies MC webhook with `channel: nightly` |

## Stable release

Do not create a stable `vX.Y.Z` tag or GitHub Release by hand: nothing builds or publishes it.

1. Open the release PR ("Release umh-core vX.Y.Z", branch `release/next`). [`prepare-release.yml`](../.github/workflows/prepare-release.yml) regenerates it on every push to `staging`. Without fragments on `staging` there is no release PR; see [Maintenance release](#maintenance-release).
2. Review the changelog in the diff. To fix an entry, fix its fragment on `staging` in a normal PR; the bot regenerates the release PR. To stop the release, request changes. Do not push to `release/next`: a release PR is the bot's single commit on top of `staging`, and the release fails otherwise.
3. Approve the PR and merge it with a merge commit.

The release ships the commit the release PR was generated from (the PR description names it), not the `staging` tip. A PR that merges into `staging` after that commit is not in this release; its fragment stays in `.changelog/unreleased/` and ships with the next one.

### Maintenance release

A release needs at least one changelog fragment. To release changes that are not user-visible, such as dependency updates or CI fixes, open a small PR to `staging` that only adds a maintenance fragment. The team decided on this entry for releases without user-visible changes. The handbook update is tracked in ENG-7942. Run this in `umh-core/`:

```bash
make changelog  # once, to install changie
./.tools/changie new --kind improvements --body "Maintenance release: internal changes only, no user-visible changes."
```

Once it is merged, the bot opens the release PR.

### Choosing the version

The bot bumps the patch number of the newest `.changelog/X.Y.Z.md`: after `0.45.2` comes `0.45.3`.

For a minor release, add the `minor-release` label to the release PR. The bot regenerates the PR as `0.46.0`. Removing the label goes back to the patch bump.

### What happens automatically

Merging the release PR starts [`release.yml`](../.github/workflows/release.yml), which runs [`release-pipeline.yml`](../.github/workflows/release-pipeline.yml). Its header explains the details.

| Job | What it does |
|-----|-------------|
| Resolve release | Finds the release commit and the version the release PR adds. Fails if the release PR changes anything other than the changelog, leaves fragments behind or does not add the newest version file, or if the newest `vX.Y.Z` tag has no published GitHub Release. |
| Build | Builds the image from the release commit with the version compiled in, pushes `vX.Y.Z`, verifies binaries |
| Tag and publish | Creates the `vX.Y.Z` tag on the release commit and the GitHub Release, then tags the image as `latest` |
| Notify the Management Console | Notifies MC webhook (see promotion logic below) |
| Sync changelog.umh.app (`sync-changelog.yml`) | Creates and merges a PR on [changelog.umh.app](https://github.com/united-manufacturing-hub/changelog.umh.app) with the release notes |
| Release notes (`update-github-release.yml`) | After the sync: writes the release notes into the GitHub Release body and links the changelog.umh.app entry |
| Sync Linear release (`linear-release.yml`) | Creates the Linear release, attaches the ENG issues in the commit range, and sets its description from the release notes |

The release notes are the version's CHANGELOG.md section, followed by the sections of the [superseded versions](#the-release-commit-is-broken). `.github/scripts/release-notes.sh` builds them for all three.

The tag is created only after the image is built and verified. The image is tagged as `latest` only after the GitHub Release is published, and only if no newer release is tagged.

If any job fails, a comment on the release PR mentions the person who merged it and links the failed run.

### MC webhook promotion logic

When notifying Management Console of a stable release:

- If the current nightly's base version matches the stable tag (e.g., nightly `v0.44.10-pre.3` → stable `v0.44.10`), the nightly is **promoted** to stable
- Otherwise, a new stable version entry is created directly

Both staging and production MC instances are notified.

## Post-release checklist

- [ ] Verify the Release workflow run succeeded
- [ ] Verify the Docker image is available: `docker pull ghcr.io/united-manufacturing-hub/umh-core:v0.X.Y`
- [ ] Verify MC shows the new version (check both staging and production)

## Troubleshooting

### A release job failed
The release PR gets a comment that mentions the person who merged it and links the failed run. Re-run the failed jobs of that run. The retry ships the same commit, and an existing tag or release is skipped.

If the failed run created the `vX.Y.Z` tag but not its GitHub Release, the next release cannot start: its Resolve release job fails while the newest tag has no published GitHub Release. Re-run the failed jobs of the failed run first, then those of the new run. If the error names a draft release, publish or delete the draft first.

### A tagged release cannot be re-run
GitHub re-runs jobs only for 30 days, and a job can keep failing. If the `vX.Y.Z` tag exists, resume the release instead: Actions > Release > Run workflow > enter `vX.Y.Z`. It skips the build and fails if the `vX.Y.Z` image does not exist. It creates the GitHub Release if it is missing, then runs the remaining jobs. It uses the workflow files on `staging`, so it includes fixes to them. If it fails, no PR gets a comment; the run summary says so. Do not create the GitHub Release by hand. Without a tag, there is nothing to resume: the next release supersedes the version.

### The release commit is broken
Merge a fix into `staging`. If the release failed before its tag was created, the next release supersedes the failed version. Only the newest version is released: it gets the tag, the image, the GitHub Release, the changelog.umh.app entry, the Linear release and the MC notification. A superseded version stays in `CHANGELOG.md` but gets none of these. If its build succeeded before the release failed, its `vX.Y.Z` image stays in GHCR. Nothing points to it: it is not `latest`, has no tag or GitHub Release, and MC is not notified. Its section is part of the newest version's release notes, and the newest version's Linear release includes its issues. If the fix has no changelog fragment (for example a CI fix with `skip-changelog-guard`), there is no release PR: add a [maintenance fragment](#maintenance-release).

If the broken version was released (it has a tag and a GitHub Release), the next release is a normal release with the fix. Its notes and Linear release cover only its own changes.

A re-run of an older release after a newer one was tagged does not move `latest` and fails on purpose before notifying MC: it would move MC's stable channel back.

### The release PR was squash-merged
The Release run fails, because only a merge commit names the commit the release PR was generated from. Nothing was tagged. Revert the squash commit on `staging` and merge the regenerated release PR with a merge commit.

### Fixing a released entry
Edit `.changelog/X.Y.Z.md`, run `make rebuild-changelog`, and commit both files. The released-section guard in PR CI rejects the change, so add the `skip-changelog-guard` label. Then re-run Actions > Update GitHub Release and Actions > Sync Changelog with the version.

### changelog.umh.app entry was not created
Re-trigger via Actions > Sync Changelog > Run workflow > enter the version. Supports `dry_run` mode for testing.

### GitHub Release body is empty or wrong
Re-trigger via Actions > Update GitHub Release > Run workflow > enter the tag name. It reads `CHANGELOG.md` from the branch the workflow runs on.

## Workflow files

| File | Purpose |
|------|---------|
| `.github/workflows/prepare-release.yml` | Keep the release PR up to date |
| `.github/workflows/release.yml` | Detect a release PR merge and start the release |
| `.github/workflows/release-pipeline.yml` | Build, tag, notify MC, publish notes |
| `.github/scripts/resolve-release.sh` | Find the release commit and the version |
| `.github/scripts/next-release-version.sh` | Compute the version of the next release PR |
| `.github/scripts/release-notes.sh` | Build the release notes from CHANGELOG.md |
| `.github/workflows/build-umh-core.yml` | Build and verify the image; notify MC for pre-releases |
| `.github/workflows/sync-changelog.yml` | Sync CHANGELOG.md to changelog.umh.app |
| `.github/workflows/update-github-release.yml` | Populate GitHub Release body from CHANGELOG.md |
| `.github/workflows/linear-release.yml` | Sync the release to Linear |
| `.github/workflows/pull-request.yml` | PR CI (calls build-umh-core.yml as reusable workflow) |
